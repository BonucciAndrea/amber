# Scout report - Amber against every reachable array language and columnar engine

Generated by `bench/scout/scout.py` + `bench/scout/report.py`. Rules, data model and
answer definitions: **`bench/scout/SCOUT_SPEC.md`**. Every number below survived an
exact answer check against the C reference; a cell that did not is shown as its failure
status instead of a time.

## 5. How to read this table - caveats, and defects found while building it

### CBQN's numbers are not float64 numbers

BQN has no user-visible float/int distinction: an array of the values `0..999`
is *stored* as narrow integers (i8/i16), and CBQN's kernels run on that storage.
So on this dataset CBQN streams roughly a quarter of the bytes the float64
engines stream, and its sort is a range-detected counting sort rather than a
comparison or radix sort over 64-bit keys. That is a real property of the
implementation and worth copying, but **`cbqn` rows on `sum_f`, `sum_i`,
`max_f`, `sort_f`, `sort_presorted`, `distinct`, `member` and `group_10` are not
like-for-like with the float64 engines** and should not be read as "CBQN's
reduction loop is 3x faster than Amber's".

### `mavg_256` is the one non-exact op

A moving average divides by a growing window count, so its summed result is
genuinely order-dependent. It is compared at a relative tolerance of `1e-9`;
every other op in this report is compared **bit-exactly** against the C
reference (`SCOUT_SPEC.md` section 2).

### Defects found in Amber while building the harness

**1. `aj` misreads a range-representation time column (correctness bug).**
Amber keeps `n+!m` in a compact *range* form. The native `` `aj `` kernel
(`ajc()`, `src/a.c`) reads that form's length as 2, so it returns a 2-element
match vector and `aj[]` then dies with `'length`. Minimal reproducer:

```k
`aj(1 501 1001 1 501 1001 1 501 1001 1 501 1001; 1000+!10;
    0 9 6 3 9 6 3 0 6 3; 3 12 9 6 12 9 6 3 9 6)
/ -> 1 11                              (2 elements, wrong)
/ writing 1000+!10 out as a literal 1000 1001 ... 1009 gives the correct
/ -> 1 11 8 5 11 8 5 2 8 5             (10 elements)
```

`0+v`, `(#v)#v` and `` `i$v `` all preserve the range form and stay broken;
`v@!#v` materialises and works. The pure-K fallback `ajmK` is correct on the same
input, so the defect is isolated to the C kernel. This matters in practice: a
trade tape whose time column is built as `1000+til n` is the normal shape, and
`aj` fails on it. `bench/scout/engines/amber.k` works around it with `mat` so the
`asof` row could be measured at all.

**2. A lambda body split across lines in a `.k` script file mis-parses.**
The `tablesort` checksum returned a non-numeric value until it was collapsed onto
one line; the same shape works at the REPL. Worth a look at the script reader.

### Notes on the other engines

- **kdb+/q needs `` `p# `` on the quote table** for `aj` to be O(log n) per row.
  Without it `asof` takes **~47 s** instead of ~88 ms. The harness applies it
  outside the timed region, which is the documented, idiomatic setup.
- **ngn/k has no hash index**: `?` and `in` are linear scans, which is why `find`
  (1326 ms) and `member` (2347 ms) are two orders of magnitude off everyone else.
  That gap is exactly the value Amber's search kernels add over its own upstream.
- **PeachQ 0.81 is an early preview.** It is correct on every op it ran, but its
  kernels are largely untuned (`group_100k` 4.1 s, `mavg_256` 11.7 s) and it has
  no `` `p# `` attribute yet - the harness asks for it and falls back.
- **J wins both high-cardinality group-bys outright** (42.6 ms at 10k groups,
  61.0 ms at 100k), beating even the hand-written C reference. Its `/.` key
  primitive is the single best-optimised group-by in this field.
