GAP:     amber 46.87 ms  vs  C 10.29 ms  (4.55x)   [Amber already beats q 0.73x]

GAP:     sort_f  282.12 ms  vs  C 79.17, NumPy 58.93, Polars 104.82

4. HOW TO READ THE CBQN COLUMN (do not chase these numbers naively)
--------------------------------------------------------------------------------
BQN has no user-visible float/int distinction. An array holding the values
0..999 is STORED as narrow integers (i8/i16), and CBQN's kernels run on that
storage. On this dataset CBQN therefore streams roughly a quarter of the bytes
the float64 engines stream, and its sort is a range-detected counting sort over
i16 rather than a radix sort over 64-bit keys.

So `cbqn` on sum_f, sum_i, max_f, sort_f, sort_presorted, distinct, member and
group_10 is NOT like-for-like. The transferable idea is the RANGE DETECTION
(item 6), not the raw ratio. When you set a target, use the C column, the J
column (group-by) or the NumPy/Polars column (sort) — those are all working on
real 64-bit data.

    `<`. kdb's growing-window semantics for msum/mavg/mmin/mmax. Null handling
    as std.k documents it. If an optimisation would change an observable result,
    it is out of scope — raise it instead of shipping it.

6. HOW TO MEASURE (use the harness, do not invent a new one)
--------------------------------------------------------------------------------
From the repo root, under WSL:

    python3 bench/scout/scout.py --build            # C ref + both Amber builds
    python3 bench/scout/scout.py --list             # engine availability
    # one op, Amber vs q vs C only, fast iteration:
    python3 bench/scout/scout.py --n 10000000 --runs 3 --warmup 2 \
        --engines amber-native,q --ops distinct_100k
    # full matrix, resumable (writes after every op):
    python3 bench/scout/scout.py --n 10000000 --runs 3 --warmup 2 \
        --timeout 110 --resume --out bench/scout/results.json
    python3 bench/scout/report.py bench/scout/results.json \
        bench/scout/results.json > bench/SCOUT_REPORT.md

The runner GATES every timing on an exact answer match against the C reference:
a cell that computes the wrong answer is printed as WRONG and its time is never
published. If your optimisation makes a cell go WRONG, it is not an optimisation.

Re-run the SAME ops before and after each change; do not compare against the
numbers in this file if you have rebuilt or the machine is busy — re-baseline.
